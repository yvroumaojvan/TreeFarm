# 🌳 TreeOfThought 思维树 v3.1（通用版 · 真搜索算法版 · 自动检测）

> 思维树把「深度思考」变成一棵看得见的树：问题 = 树干，推理路径 = 分支，
> 每轮分支收拢成「共识」= 树的新芽，最终答案 = 果实。
> **v3.0 升级**：不再只是"分点输出"，而是**真正的树搜索**——
> 分支要评分、低分要剪枝、死路要回溯、状态要管理（对标 Princeton ToT 论文的 LLM+搜索架构）。
> 本项目由 Operit 平台 TreeOfThought 插件移植而来，专为纯文本/CLI 环境设计——用符号画树，不依赖图片。

## 0. 开关与触发方式（最重要，先读这个！）

思维树**默认关闭，绝不自动使用**。它由用户的一句话控制：

| 用户说的话 | 效果 |
|-----------|------|
| 「开启思维树」/「打开思维树」/「用思维树」 | 🟢 **开启**：之后遇到复杂问题就用思维树，直到用户说关闭 |
| 「思维树回答：<问题>」/「思维树：<问题>」/「用思维树想一下<问题>」 | 🟢 **单次使用**：只这一次用思维树 |
| 「关闭思维树」/「关掉思维树」/「不用思维树了」 | 🔴 **关闭**：恢复正常回答 |
| 「关闭自动检测」/「关掉自动检测」/「别问了」 | 🔴 **关闭自动检测**：AI 不再主动提醒，回到"不说关键词就不用"的老规矩 |
| 「开启自动检测」/「打开自动检测」 | 🟢 **开启自动检测**（**默认开启**）：AI 自动评估任务，复杂任务主动询问是否开思维树 |

**执行规则（状态机，按顺序判断）**：
1. 用户没说"思维树"三个字 → **默认关闭**。但先查【自动检测】开关：
   - **自动检测开启**（默认）→ 跳到第 7 步评估
   - **自动检测关闭** → 绝不使用本技能，正常回答即可
2. 用户说了「开启思维树/打开思维树/用思维树」→ 进入**开启状态**：本次会话内**持续生效**，
   之后遇到复杂问题**自动**用思维树，**无需用户每轮重复说「开启」**（说一次，一直开）
3. 用户说了「思维树：问题」→ 只对这一个问题用一次，用完**不改变**开关状态
4. 用户说「关闭思维树/关掉思维树/不用思维树了」→ **关闭状态**：立即失效，恢复正常回答
5. **本次会话结束**（CLI/终端重启、新开会话）→ 自动回到**默认关闭**（自动检测也回到**默认开启**）
6. 拿不准时，可以反问一句"需要我用思维树深度思考吗？"，听用户指挥
7. **自动检测评估**（仅在第 1 步自动检测开启时执行，见 0.6 节）：
   - 判断这个任务**是否需要深度思考**（复杂决策/深度分析/多角度对比/方案设计/严谨推理/修 bug/写代码 → 需要；闲聊/简单问答/信息查询/单步操作 → 不需要）
   - **需要** → 主动询问一句，**绝不擅自开启**："这个任务有点复杂，需要开思维树深度思考吗？"
   - 用户同意（「开启」「好」「用」）→ **自动进入开启状态并运行**
   - 用户拒绝（「不用」「普通回答」）→ 正常回答，本次任务不再追问
   - **不需要** → 不提醒，正常回答

## 0.5 执行模式（一边思考一边动手，默认开启）

思维树不只是"想"，还能"做"——**思考过程中可以直接使用宿主 AI 的一切工具能力**：
读文件、搜索代码、跑测试、执行命令、写文件、git 操作……宿主 AI 会什么，思维树就会什么。
这正是为"修 bug、写代码"类问题设计的：**越难的问题、藏得越深的 bug，分支越多越能挖出来**，
挖出来还要当场修掉。

**默认开启**（用户策略：所有功能默认开启）。用户说「思维树只思考不动手」→ 关闭，只输出分析不动文件。

**v3 工具**（有终端环境的 agent，如 Claude Code / Qwen Code / Cursor / Gemini CLI）：
- `scripts/tree-search.js` —— **树搜索管理器**（零依赖 Node）：维护树的搜索状态（节点/评分/剪枝/回溯），
  提供 `init / expand / score / select / prune / backtrack / signal / converge / render` 命令
- `scripts/render-tree.js` —— 文字树渲染器（支持渲染 tree-search 状态，带状态徽章）

**修 bug / 写代码场景的流程增强**（在搜索循环中嵌入工具操作）：
1. **先侦察再思考**（树干成形后、分支生长前）：先读相关文件、搜索关键词、看 git 记录，
   摸清现状——**分支推理必须基于真实代码，不许空想**
2. **边想边验证**：分支里提出的每一个可疑点，用工具确认（打开对应文件、跑测试或命令复现），
   验证是真 bug 还是误判——验证过的分支才是真思考
3. **直接动手修**：确认根因后直接写文件修复，修复完跑测试/命令验证，确认没改坏别的东西
4. **输出修复报告**：改了哪些文件、为什么改、验证结果（用文字树展示推理过程 + 修复结论）

**执行规则**：
- 需要工具操作时直接操作，不用停下来"请示"——思考与动手交替进行
- 只读操作（读/搜/git log）随时可用；**写操作在修复方案确认后执行**（方案 = 分支收敛出的共识）
- 无法执行工具的环境（纯聊天 AI 如豆包/ChatGPT）：自动降级为第 8 节「纯聊天降级协议」
- 纯分析类问题（决策/对比）不强制动手，正常思考输出即可

## 0.6 自动检测（默认开启，智能提醒不打扰）

> 解决的问题：用户经常忘了说「开启思维树」，等想起来时已经绕了远路。
> 自动检测 = 让 AI 当"门卫"：任务一来先判断值不值得用思维树，值得就**问一句**，
> 用户点头就开。**它只提醒、绝不擅自开启**——思维树依然只有用户说了才算数。

### 开关
- **默认开启**（每次新会话都回到开启）
- 用户说「关闭自动检测」/「关掉自动检测」/「别问了」→ 关闭：AI 不再主动提醒，完全回到老规矩
- 用户说「开启自动检测」/「打开自动检测」→ 开启

### 什么时候会问（评估标准）
用户的任务命中以下任一类型 → **值得问**：
| 任务类型 | 例子 |
|---------|------|
| 复杂决策 | 该不该辞职创业？A/B 方案选哪个？ |
| 深度分析 | 这个现象的本质是什么？销量为什么下滑？ |
| 方案设计 | 如何实现某个目标？系统怎么设计？ |
| 多角度对比 | 对比两个方案/产品/路线的优劣 |
| 需要严谨推理 | 数学/逻辑推导、学术问题、需要一步步验证假设 |
| 修 bug / 写代码 | 藏得深的 bug 定位、跨模块耦合分析、功能设计实现 |

以下类型 → **不要问**（杀鸡不用牛刀，问了反而烦人）：
闲聊、寒暄、简单问答（"1+1=?"）、信息查询（"今天几号"）、单步操作（"帮我读这个文件"）、
情绪倾诉（先接住情绪，别打断）

### 怎么问（一次一句，别啰嗦）
- 标准问法："这个任务有点复杂，需要开思维树深度思考吗？"
- 或更贴心的："我可以普通回答，也可以开思维树把细节挖深一点，你要哪个？"
- **只问一次**：用户拒绝后，本次任务不再追问，直接正常回答

### 用户的回应怎么处理
| 用户说 | 处理 |
|--------|------|
| 「开启」「好」「用」「可以」 | 🟢 自动进入**开启状态**，用思维树跑当前任务，之后持续生效 |
| 「不用」「普通回答」「先不用」 | 🔴 正常回答，本次任务不追问 |
| 「思维树」相关词 | 按第 0 节状态机正常处理 |

### 红线（宁缺毋滥，别烦人）
1. **绝不擅自开启**——自动检测只负责"提醒+询问"，开关永远握在用户手里
2. **简单任务绝不提醒**——问多了用户会烦，宁可不问也不能乱问
3. **不重复追问**——同一任务只问一次；用户拒绝后马上安静干活
4. 情绪倾诉类话题**直接温柔回应，禁止打断问"要不要开思维树"**——先当人，再当工具

## 1. 核心思想（v3：搜索算法驱动）

- **真正的树搜索**：一个问题从多个独立维度同时推理，分支**评分 → 剪枝 → 深挖 → 回溯**，
  而不是一条直线想到底。默认 **beam search（束搜索）**：每层保留 Top-K 高质量分支，其余剪掉。
- **双重归纳**：每轮结束做两种归纳——①**共识**（多数分支共同指向的结论）②**弱信号**（少数分支的
  非常规观点/边界条件）。**弱信号不是噪声，往往是关键盲点**，必须单列展示。
- **动态收敛**：相邻两轮结论高度重合（≥90%）就提前收工，不浪费 token。
- **摘要链**：每轮只把 ≤200 字摘要带给下一轮，不传完整历史，省 token 且防跑偏。
- **状态管理**：每个分支有明确状态（待展开/已展开/已评分/剪枝/死路），搜索过程可中断、可续跑、可复盘。

## 2. 使用场景（仅在思维树【已开启】时适用）

开关已开启（用户说过「用思维树」）时，遇到以下类型的问题就使用思维树：

| 类型 | 例子 |
|------|------|
| 复杂决策 | 该不该辞职去创业？A 和 B 方案选哪个？ |
| 深度分析 | 这个现象的本质是什么？有哪些被忽略的因素？ |
| 方案设计 | 如何实现某个目标？有哪些路径和风险？ |
| 多角度对比 | 对比两个方案/两个产品/两条路线的优劣 |
| 需要严谨推理的问题 | 需要一步步推导、验证假设的学术/技术问题 |
| 修 bug / 写代码 | 藏得深的 bug 定位、跨模块耦合分析（配合树场机制更佳） |

**开关未开启（默认状态）**：以上问题一律正常回答，不用思维树。

## 3. ★ 搜索算法（v3 核心，对标专业版）

### 3.1 搜索策略（三选一，默认 beam）

| 策略 | 选择下一个分支的规则 | 适用场景 |
|------|---------------------|---------|
| **beam（默认）** | 每层先全部评分，保留分数 Top-K（束宽），从最高分分支优先深挖 | 通用——质量优先，兼顾广度，专业工具标准做法 |
| **bfs** | 广度优先：先把一层铺满再深入 | 需要全面覆盖、不想漏任何方向时 |
| **dfs** | 深度优先：一条路深挖到底，走不通回溯换路 | 问题窄而深、已知大致方向时 |

### 3.2 节点状态机（每个分支必须有一个状态）

```
open（待展开）→ expanded（已展开，长出子分支）→ scored（已评分）
                                              ↘ pruned（剪枝：分数低于束宽线）
                                              ↘ dead_end（死路：回溯标记，记录原因）
```

- **open**：生成了但还没深挖的分支（候选池）
- **expanded**：已经长出子分支（深挖完成一层）
- **scored**：已按评分表打分，等待被选中继续深挖，或被剪枝
- **pruned**：束宽之外的落选分支（✂️），不再投入 token
- **dead_end**：推理走死（💀），记录死因，触发回溯

### 3.3 四维评分表（每个分支都要打，0~1 分）

| 维度 | 权重 | 打分标准（问自己这些问题） |
|------|------|--------------------------|
| **evidence 证据** | 35% | 推理里有具体事实/数字/代码引用吗？有具体数据=0.8~1.0；只有断言=0.3 以下 |
| **relevance 相关** | 30% | 与树干/父分支的问题直接相关吗？还是跑题了？ |
| **novelty 新颖** | 20% | 与其他分支的观点重复吗？全新角度=高分；重复共识=低分 |
| **verifiable 可验证** | 15% | 结论能被工具/数据/实验验证吗？能验证=高分；纯玄学=低分 |

**综合分 = 0.35×证据 + 0.30×相关 + 0.20×新颖 + 0.15×可验证**（与 tree-search.js 计算一致）

**打分红绿线**：
- 🔴 证据 <0.3 的分支 = 空想分支，直接标记 dead_end（别浪费展开机会）
- 🟢 综合分 ≥0.75 的分支 = 优先深挖
- 🟡 0.5~0.75 = 保留观察；<0.5 = 束宽内才留，否则剪枝

### 3.4 剪枝规则（beam 束宽）

- 每层分支数 > 束宽（默认 4）时，按综合分排序，**保留 Top-K，其余剪掉**
- 剪掉的分支标记 `pruned`，**不再展开、不再投入 token**
- 剪枝要诚实：被剪分支如果后来发现很重要（弱信号可能藏在低分里），
  在最终输出里留一句"剪枝记录"提示用户可回头深挖

### 3.5 回溯规则（死路处理）

分支满足以下任一条件 → 标记 `dead_end` 并**回溯**：
1. 推理无进展（新分支只是重复父分支的观点，证据分 <0.3）
2. 关键前提被证伪（工具验证发现假设不成立）
3. 数据/资料获取失败，无法继续

**回溯动作**：回到最近的、仍有待展开分支的祖先节点，从那里换一条路继续；
如果整条路径都死了，回到树干重新分支。**回溯不是失败**——它证明了"这条路确实不通"，
避免在死路上浪费更多 token（这正是思维树比直线思考强的地方）。

## 4. 数据模型（v3：带状态与评分的树）

```
{
  "trunk": "精简后的问题（树干）",
  "strategy": "beam | bfs | dfs",
  "beam_width": 4,
  "max_depth": 3,
  "nodes": {
    "n_1": {
      "id": "n_1", "parent": null, "depth": 0,
      "type": "trunk", "content": "问题",
      "status": "expanded", "children": ["n_2", "n_3", ...],
      "score": null, "pruned": false, "dead_reason": null
    },
    "n_2": {
      "id": "n_2", "parent": "n_1", "depth": 1,
      "type": "branch",
      "content": { "dimension": "维度名", "hypothesis": "假设", "reasoning": "推理", "conclusion": "结论" },
      "status": "scored", "children": [],
      "score": { "evidence": 0.9, "relevance": 0.8, "novelty": 0.6, "verifiable": 0.7, "total": 0.79 },
      "pruned": false, "dead_reason": null
    }
  },
  "order": ["n_1", "n_2", ...],
  "stopReason": "converged | maxDepth | deadEndAll",
  "summary": "推理摘要",
  "answer": "最终答案"
}
```

有终端环境时，这份状态由 `tree-search.js` 自动维护（见第 7 节）；纯聊天环境由 AI 在对话里手动维护。

## 5. ★ 搜索循环工作流（v3 替代原六步）

严格按以下循环执行（每步都要真实思考，不许跳步）。**默认配置：beam 搜索 · 束宽 4 · 最大深度 3 · 每层 4~8 个分支**。

**第 1 步 · 树根净化**（可选）
用户提供了资料/上下文 → 先清洗为 ≤500 字核心摘要；无资料则跳过。

**第 2 步 · 树干成形**
把原始问题精简为 ≤100 字核心骨架：去情绪、去冗余、去重复，只留问题本质。

**第 3 步 · 分支生长（expand）**
基于树干生成分支。**默认每层 4~8 个独立分支**（用户可自定义）。铁律：
- **维度必须按问题领域自主选择**——这是思维树质量的生死线！分支维度必须长自问题本身的具体内容，禁止万能模板套话
- 每个分支是完整的「假设 → 推理 → 结论」三段式
- 精炼紧凑：推理 ≤100 字，结论 ≤80 字
- 分支之间要真正独立，覆盖不同角度，允许互相矛盾

**维度选择示范**（❌ 模板垃圾 vs ✅ 真思考）：

| 问题 | ❌ 万能模板（禁止！） | ✅ 按领域长出的真维度 |
|------|---------------------|----------------------|
| 该不该辞职去创业？ | 技术可行性/成本效益/用户体验 | 财务安全边际/市场验证信号/能力与机会成本/家庭支持与退路 |
| 某数学猜想是否成立？ | 技术可行性/成本效益/用户体验 | 特殊情形验证/反例边界/已知定理关联/计算验证 |
| 选哪种数据库？ | 技术可行性/成本效益/用户体验 | 数据规模与增长/一致性要求/运维成本/团队熟悉度 |
| 为什么销量下滑？ | 技术可行性/成本效益/用户体验 | 渠道流量变化/价格与竞品/产品口碑/用户流失路径 |

**判断标准**：把分支维度拿去套别的领域——如果能套用，就是模板；套不上，才是真思考。

**第 4 步 · 评分（score）**
按第 3.3 节四维评分表，给每个分支打分（evidence/relevance/novelty/verifiable + 综合分）。
打分必须诚实：空想分支证据分就是低，重复分支新颖分就是低。

**第 5 步 · 剪枝（prune）**
分支数 > 束宽（默认 4）→ 按综合分保留 Top-K，其余标记 pruned。剪枝记录留档。

**第 6 步 · 深挖与回溯（select → expand → backtrack）**
- 从存活分支中选综合分最高的（beam 策略），**深入一层**（第 3~5 步再来一轮）
- 某分支推理走死（第 3.5 节条件）→ 标记 dead_end，**回溯**到最近有存活分支的祖先继续
- 深度达到 max_depth（默认 3）→ 停止深挖

**第 7 步 · 双重归纳（signal）**
每层结束做两种归纳：
- **共识**：多数分支共同指向的结论（1~2 句）
- **弱信号**：仅 ≤30% 分支出现的非常规观点、边界条件、被忽略的要点。逐条列出（见第 6 节）

**第 8 步 · 收敛检测（converge）**
- 相邻两层分支结论高度重合（混合相似度 ≥90%）→ 收敛，停止
- 或达到 max_depth → 停止
- 或所有路径都成死路 → 停止（诚实报告：此问题用树搜索未能收敛出可靠答案）

**第 9 步 · 最终输出**
- 渲染**完整文字树**（带状态徽章：评分/剪枝/死路/回溯痕迹）
- 输出最终答案（结论先行）+ 推理摘要（200~300 字）+ 弱信号记录 + 停止原因 + 剪枝记录
- **修复类问题（执行模式开启时）**：按共识方案直接写文件修复 → 跑测试/命令验证 → 输出修复报告

## 6. ★ 弱信号检测（思维树的核心特色，v3 算法化）

> 原版 ToT（Tree of Thought）论文只做 BFS/DFS 多分支搜索，**弱信号检测是本项目原创增量**——
> 共识代表主流方向，弱信号代表被主流忽略的可能性，它往往藏着决定性盲点。这是思维树区别于普通"多角度分析"的灵魂。

### 什么是弱信号

- **定义**：仅出现在 ≤30% 分支（通常是 1 个）中的观点——非常规角度、边界条件、反例、被忽略的要点。
- **为什么重要**：多数分支共同指向的结论=共识（安全但平庸）；少数分支提出的异议=弱信号（危险但关键）。重大决策翻车，几乎都翻在被忽略的弱信号上。
- **例子**：4 个分支都在讨论辞职创业的收益，只有 1 个分支提到"先副业试水更稳"——这就是弱信号，可能是最优解的引子。

### 怎么检测（v3：算法 + AI 复核双轨）

1. **工具聚类**（有终端）：`node tree-search.js signal [深度]` 自动统计——把各分支结论
   按文本相似度聚类（中文用 bigram 余弦、英文/代码用 trigram），计算每簇出现频率
2. **AI 语义复核**（必须做）：工具的聚类是近似（算法不懂语义，同义不同词可能漏聚），
   AI 用自己的语义理解复核一遍，把语义相同但措辞不同的观点合并统计
3. **判定**：合并后出现频率 ≤30% 的观点簇 → 弱信号；>30% → 共识方向

### 怎么用（三件事，缺一不可）

1. **必须单列展示**：弱信号在文字树中用 `⚡` 单独列出，标注出现比例（如 `1/4 分支提及`），不许藏在共识里糊弄过去
2. **必须带进下一轮**：下一轮分支生成时把弱信号作为验证方向（"共识 + 弱信号"一起喂给下一轮），验证它是真信号还是噪声——这是弱信号的深化机制
3. **必须记入最终输出**：最终答案的推理摘要里保留弱信号记录，让用户看到"被多数人忽略但值得警惕的点"

### 诚实红线

- 弱信号**不许编造**：只有真出现于少数分支的观点才能叫弱信号
- 弱信号**不许压制**：即使它和共识矛盾（尤其当它和共识矛盾时！），也要原样展示
- 工具聚类结果**不许照抄**：算法可能漏聚或错聚，AI 复核是义务不是可选

## 7. 与 tree-search.js 协作协议（有终端环境的 agent 必读）

搜索循环的每一步，用 tree-search.js 维护真实状态（一个命令一个状态，自动持久化到 `.tree_state.json`）：

| 工作流步骤 | tree-search.js 命令 | 说明 |
|-----------|---------------------|------|
| 树干成形 | `node scripts/tree-search.js init --strategy beam --beam 4 --depth 3 "问题"` | 初始化树（可改 bfs/dfs） |
| 分支生长 | `node scripts/tree-search.js expand <节点id> '[{...分支JSON...}]'` | 分支内容由 AI 生成 |
| 评分 | `node scripts/tree-search.js score <节点id> '{"evidence":0.9,...}'` | 四维分由 AI 按评分表打 |
| 选择下一个 | `node scripts/tree-search.js select` | 算法按策略选（beam=最高分） |
| 剪枝 | `node scripts/tree-search.js prune` | 束宽外的自动标记 pruned |
| 回溯 | `node scripts/tree-search.js backtrack <节点id> "死因"` | 标记 dead_end 并返回可回退点 |
| 弱信号 | `node scripts/tree-search.js signal [深度]` | 自动聚类 + 频率统计（AI 复核语义） |
| 收敛 | `node scripts/tree-search.js converge` | 相邻两层结论相似度检测 |
| 渲染 | `node scripts/tree-search.js render` 或 `node scripts/render-tree.js .tree_state.json` | 带状态徽章的文字树 |

**协作原则**：**AI 出内容、出判断（决策者），工具管结构、管状态（算法）**——
AI 负责生成分支、打分、判定死路；工具负责维护树、按策略选择、记录剪枝回溯。两者结合才是真正的树搜索。

**中断恢复**：状态在 `.tree_state.json`，任何时候都可以 `node scripts/render-tree.js .tree_state.json` 看当前进度，继续搜索。

## 8. 纯聊天 AI 降级协议（无终端，如 ChatGPT / 豆包 / Kimi / DeepSeek）

没有本地脚本时，AI 在对话里**手动模拟搜索循环**（保持同样的算法骨架，只是用手记状态）：

1. 树干成形（≤100 字）
2. 分支生长：生成 4~8 个独立分支（维度按领域选，铁律不变）
3. **评分**：每个分支列四维分（证据/相关/新颖/可验证）和综合分，用表格展示——不许跳过评分直接给结论
4. **剪枝**：保留 Top-4（束宽），其余标注 ✂️（说明剪枝理由）
5. **深挖**：选最高分分支深入一层（重复 2~4 步）
6. **回溯**：某分支走死 → 标 💀 + 原因，回退到存活的祖先分支继续
7. **归纳**：共识 🧡 + 弱信号 ⚡（带出现比例）
8. **收敛**：两轮结论一致 → 停止；到最大深度 3 → 停止
9. **输出**：完整文字树（含评分/剪枝/死路痕迹）+ 最终答案 + 弱信号 + 停止原因

纯聊天版与工具版**推理质量等价**——算法骨架是协议的一部分，只是记账方式不同（手记 vs 工具记）。

> 💡 **省流模式（纯聊天省钱）**：默认的逐分支评分表在纯聊天环境会让输出明显变长。
> 用户说「思维树省流」→ 评分环节只输出每分支综合分 + Top-K 剪枝线（省略四维明细表），
> 分支数默认降到 4、深度默认 1 层；说「思维树恢复默认」→ 回到完整评分模式。
> 有终端环境时无需省流——tree-search.js 的记账不占对话 token。

## 9. Token 优化机制（省钱！）

- **摘要链**：每层结束生成 ≤200 字摘要，下一层只传摘要，不传完整历史
- **剪枝省 token**：束宽之外的分支**不展开**（v3 最大省钱点——差的路线不浪费 token）
- **死路止损**：证据分 <0.3 的分支立即回溯，不继续深挖
- **提前收敛**：相邻两层结论重合 ≥90% 可提前停止
- **默认配置**：束宽 4 × 深度 3（可自定义）
- **字数红线**：推理 ≤100 字/条、结论 ≤80 字/条、树干 ≤100 字、资料摘要 ≤500 字

## 10. 配置项（默认值 + 用户自定义）

**默认配置**：

| 参数 | 默认 | 范围 | 说明 |
|------|------|------|------|
| 搜索策略 | **beam** | beam / bfs / dfs | 束搜索（专业版标准） |
| 束宽（每层保留分支数） | **4** | 2~8 | 剪枝线，越大越广但越贵 |
| 最大深度（深挖层数） | **3** | 1~5 | 迭代上限 |
| 每层分支数 | **4~8** | 2~12 | 生成宽度（首层可更宽） |
| 收敛阈值 | 0.9 | 0.5~1 | 相邻两层结论重合度 |

**用户自定义（一句话生效，无需改文件）**：

| 用户说的话 | 效果 |
|-----------|------|
| 「思维树 3 分支 1 轮」 | 🟢 本次按 3 分支、1 层执行 |
| 「用思维树 8 分支 3 层」 | 🟢 本次按 8 分支、3 层执行 |
| 「思维树用 dfs 搜索」/「思维树深度优先」 | 🟢 改用深度优先策略 |
| 「思维树束宽 6」 | 🟢 束宽调到 6 |
| 「思维树 收敛阈值 0.8」 | 🟢 调整收敛阈值 |
| 「思维树恢复默认」 | 🟢 回到默认（beam · 束宽4 · 深度3） |

**解析规则**：从用户指令中提取「数字 + 分支」「数字 + 轮/层」和「bfs/dfs/beam」，
没提到的部分用默认值。示例：「思维树 5 层 6 分支」→ 5 层、每层 6 分支；「思维树 dfs」→ dfs 策略。

## 11. 质量红线（踩坑换来的教训）

1. **分支维度按领域选**（生死线）：禁止「技术可行性/成本效益/用户体验」万能模板——数学命题就用数学维度（特殊情形/反例边界/定理关联/计算验证），商业决策就用商业维度（财务/市场/能力/家庭），技术选型就用技术维度（规模/一致性/运维/团队）。**自查方法：把维度拿去套别的领域，套得上就是模板，必须重做**
2. **分支必须结合问题具体内容做真推理**：推理里要有具体数字、事实、机制（如"回本周期 9~18 个月""6 个月存款不够"），不是套话、不是换个说法重复问题
3. **评分必须诚实**：空想分支证据分就是低，重复分支新颖分就是低——不许为了"好看"给高分，评分是剪枝和回溯的依据，撒谎等于自废武功
4. **剪枝和回溯要留痕**：输出树里要能看到 ✂️ 和 💀 标记，让用户知道"这条路试过、为什么放弃"——这是树搜索比直线思考的可信度来源
5. **简单问题不要触发思维树**，杀鸡不用牛刀
6. **答案结论先行**：先给 1~2 句直击核心的结论，再补 2~4 条关键依据、风险与不确定性、行动建议，150~300 字，不要花里胡哨
7. **弱信号必须诚实**：只有真出现于少数分支的观点才叫弱信号，不许编造；工具聚类结果要 AI 语义复核
